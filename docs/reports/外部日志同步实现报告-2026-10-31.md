# 外部日志同步实现报告（2026-10-31）

## 1. 需求与来源

用户要求（原话）：根据自己设定的呼号，自动从 LoTW 或者 QSL 上获取通联信息并更新到系统中；并追加约束「把填写账号之类的做成页面供填写，而不是直接写死在里面」。

- 「自己设定的呼号」= `StationProfile.spec.myCallSign`。
- 「自动」= 定时任务按配置间隔运行，同时保留页面手动触发。
- 「页面填写账号」= 账号名与密码全部走前端表单，密码写入 Halo `Secret`，代码与配置里没有任何硬编码凭据。

设计基线：`docs/plans/外部日志同步设计基线.md`（本次先出基线、再编码，符合 `agents.md` 的约束性要求）。

## 2. 数据源调研结论（observed / documented）

| 数据源 | 官方接口情况 | 本次采用的做法 |
| --- | --- | --- |
| ARRL LoTW | 无编程接口（ARRL-LoTW 邮件列表原话：There is no defined programmatic interface） | 带查询参数的 ADIF 下载地址 `https://lotw.arrl.org/lotwuser/lotwreport.adi`，`qso_query=1`、`qso_withown=yes`，游标用 `qso_qsorxsince` |
| QRZ Logbook | 有官方 Logbook API：`POST https://logbook.qrz.com/api`，`ACTION=FETCH`，`OPTION` 支持 `ALL`/`AFTERLOGID`/`MAX`/`TYPE:ADIF`，返回 `key=value&` 串含 `RESULT`/`REASON`/`ADIF` | 直接按官方契约实现，游标取 ADIF 中 `APP_QRZLOG_LOGID` 的最大值，分页 `MAX:250` |
| Club Log | 仅上传有文档，整本下载无官方文档 | 不实现（未核实，不做猜测性适配） |
| eQSL | `DownloadInBox` 是收件箱语义（官方原文：the InBox does NOT contain anything like the contents of the user's station log） | 不实现（语义是收卡不是通联日志） |

功能命名统一为「外部日志同步」，不使用 LoTW 商标（ARRL 商标条款限制第三方产品名使用）。

### 2.1 官方文档复核与据此做出的修正（2026-10-31 补）

按用户要求上网核对同步方式是否与官方文档一致，权威来源取 ARRL 自己的页面 `https://www.arrl.org/adif`（比论坛帖权威）与 `https://www.qrz.com/docs/logbook/QRZLogbookAPI.html`。结论：整体做法成立，但有三处与官方语义不符，已改：

| 发现（官方原文要点） | 原实现 | 已改为 |
| --- | --- | --- |
| `qso_qsorxsince` “Ignored unless qso_qsl="no"”；`qso_qsl` 默认 yes 只返回 QSL 记录 | 已带 `qso_qsl=no` | 无需改，保留并在注释中标明理由 |
| `qso_mydetail=yes` 才返回本台站址字段（`MY_GRIDSQUARE` 等） | 未带该参数，本台网格取不到 | `buildQueryUrl` 追加 `qso_mydetail=yes` |
| 官方推荐增量：记住返回的 `APP_LoTW_LASTQSORX`，用它作下次 `qso_qsorxsince` | 游标取本批最大 `QSO_DATE`（日期粒度，同一天多次同步会重复或漏） | 新增 `resolveCursor()`，优先读响应头部 `APP_LOTW_LASTQSORX`，取不到才回退最大 `QSO_DATE` |
| 「In a future release, Logbook will not emit the MODE field…the mode value will be provided via APP_LOTW_MODE」 | 只读 `MODE`，缺失时模式为空 | `MODE` 为空时回退 `APP_LOTW_MODE`，并把它加进已消费字段集，避免重复进备注 |
| `AFTERLOGID` 语义是“greater than or equal”，官方分页建议“highest value plus one” | 游标取上批最大 `APP_QRZLOG_LOGID`，等于值会重复返回 | `maxLogId()` 返回 `max + 1` |
| “When the option ALL is given, only TYPE and STATUS may also be specified” | 首次 `ALL`、增量改用 `AFTERLOGID` 时已不带 `ALL` | 无需改，已加注释与测试锁定 |

未采用的写法：论坛流传的 `qso_detail=yes` 未出现在官方文档中，不实现。

## 3. 实现范围

### 3.0 定时同步（本轮新增）

- `api/QslLogSyncScheduler.java`（新增）：`@Scheduled(fixedDelay = 60_000L, initialDelay = 120_000L)`，方法直接返回 `Mono<Void>` 由 Spring 调度器订阅（`documented`：Halo 插件调度文档说明 Spring Framework 6.1 起自动订阅 `@Scheduled` 方法返回的响应式类型，并在插件上下文关闭时取消；本项目依赖的 Spring 为 7.x，条件成立）。
- `QslManagementPlugin.java`：类级 `@EnableScheduling`。
- `QslLogSyncService`：新增 `runDueSyncs()`、`static boolean isDueForScheduledSync(LogSyncProfile, Instant)`（纯函数，便于测试）、`recordProfileFailure(...)`；定时作业操作者记为「外部日志同步（定时）」，客户端标记 `scheduler`。
- 到期判定：已启用 + 已开启自动同步 + 距上次同步超过 `syncIntervalMinutes`（下限 60 分钟）三者同时满足；从未同步过立即执行一次；时间戳损坏按到期处理。同一配置存在未结束作业时跳过本轮。
- 失败处置：写回最近错误与连续失败次数，并把最近同步时间推进到当前时间，使失败也遵守间隔，避免上游故障时连续冲击。

## 4. 同步语义

- 判重键：`场景|呼号|日期|时间|时区|模式|频率`，各段 `trim → 大写 → 去空白`，与前端 ADIF 导入同一规则。
- `SKIP`（保留已有）：命中判重键直接跳过并计入跳过数。
- `OVERWRITE`（覆盖已有）：只覆盖通联事实字段（呼号、日期、时间、时区、频率、模式、收发信号报告、操作员、本台网格、对方 QTH），不覆盖备注与人工维护的设备、天线字段。
- 单条记录缺呼号或缺合法日期时间时记为失败明细，不阻断整批；失败明细最多 200 行。
- 记录资源名按既有 `QSO<序号>` 规则续号：扫描现有记录的最大序号后续排，避免与既有记录撞名。
- 游标：LoTW 用日期，QRZ 用最大日志 ID；每次同步成功后写回 `LogSyncProfile.status.lastCursor`。

## 5. 安全

1. 凭据只写 Halo `Secret`（OPAQUE），`LogSyncProfile.spec` 只存 Secret 名；接口不回显密码，保存成功后输入框清空。
2. 出站错误信息只包含异常类型与安全描述，**不拼接请求地址**——LoTW 的地址里带密码，这是本次最高风险点，单独处理。
3. 出站域名固定为 `lotw.arrl.org` 与 `logbook.qrz.com`，不做用户可配的基础地址。
4. 上游返回内容先判形（是否像 ADIF），登录页/错误页不当作日志解析。
5. 同步编排加并发保护，同一配置不会并发跑两次；超时未收尾的作业按陈旧处理。
6. 每次保存配置、保存凭据、手动同步都写审计日志，审计内容不含密码。

### 11.2 顺带修掉的两个真 bug

1. **删除链路的内层 Mono 在装配期就执行**：`.then(deleteSecret(...))`、`.then(deleteJobsOfProfile(...))`、`.then(auditService.appendAuditLog(...))` 都是把方法**调用结果**传给 `then`，方法体在装配阶段就跑了——「同步进行中拦截删除」这条前置检查形同虚设，还可能在检查失败前已经删掉 Secret。全部改为 `Mono.defer(...)` 包裹。这个问题是新写的 `QslLogSyncDeleteTest` 逼出来的（`NullPointerException: newLast` 直接指到 `MonoIgnoreThen.shift`）。

### 11.6 2.3.39 实测仍然「保存不上」的真根因（2.3.40 修复）

用户装上 2.3.39 后反馈凭据依旧保存不上。定位到 `QslLogSyncService.saveCredential`：

```java
return loadSecret(secretName)
    .flatMap(current -> upsertSecret(secretName, profileName, current, account, password, passwordRequired))
    ...
```

`loadSecret` 在 Secret 不存在时返回 `Mono.empty()`，**`flatMap` 于是根本不会执行**——首次保存凭据时既不创建 Secret 也不报错，后面的配置 `update` 照常成功，页面于是「保存成功但一直显示未配置」。这是一条只有首次保存才会走进的路径，2.3.38 及以前同样存在（当时读的是 `spec.credentialSecretName`，空串时 `loadSecret` 直接短路，问题更早发生）。

修复：接一个 `switchIfEmpty(Mono.defer(() -> upsertSecret(secretName, profileName, null, ...)))`，让首次保存真正走创建分支。

新增 `src/test/java/com/bi1kbu/qslmanagement/api/QslLogSyncCredentialTest.java` 4 项，其中「首次保存凭据要真的创建 Secret」直接锁死这条路径；另三项覆盖「已有 Secret 时密码留空表示不修改」、「LoTW 只填账号要拒绝而不是写半截凭据」、「QRZ 只要 Key 密码可空」。

测试夹具也暴露一个真实约束：`QslLogSyncService` 的 `requiresPassword` 依赖注入的数据源注册表，装配空列表时所有数据源都会被当成「必须密码」。测试因此必须装配真实适配器。

## 11.8 第三轮实测：「只拉到一条记录」（2.3.41 / 2.3.42）

2.3.40 之后用户反馈「可以了，但是只拉到一条记录」，并给出一条样例 `BI3AMG · 20261023 091800 · FT8 · 7.07553`——正是账号里最新的一条。

诊断分两步：

1. **先让信息可见（2.3.41）**：`TestResult` 增加 `records`，最多 20 条压平样例行，页面直接列出「上游返回的记录样例」。此前只有总条数，用户无法区分「我的日志本来就这么少」和「程序有 bug」。

## 11.9 第四轮实测：装上 2.3.42 仍然只拉一条（2.3.43）

用户装 2.3.42 后「立即同步」仍是「拉取 1 / 跳过 1」，配置行的「数据游标」停在 `2026-10-23 09:19:02`。

这是**旧游标把后续增量锁死**：2.3.41 之前那几次「只拉到最新一条」的成功同步，把那条记录的时间写成了 `lastCursor`；2.3.42 的 `1900-01-01` 起点只在「游标为空」时生效，因此后续增量一直从错误的起点往后查，永远只回最新一条并判重跳过。用户手上没有任何办法清掉这个游标。

因此新增 `QslLogSyncService.resetCursor(profileName, operator, clientIp)` 与 `POST /log-sync/profiles/{profileName}/reset-cursor`：清空 `lastCursor`、`lastError`，连续失败计数归零，不删任何已同步记录；同步进行中返回 409 `QSL-409-LS-0001`。页面「同步操作」工具栏加「重置游标」按钮，提示「下一次立即同步会按全量重新拉取」。

教训：**凡是会持久化的增量游标，都必须提供重置入口**——否则一次错误的起点会永久污染后续所有同步，而页面上看起来只是「数据少」。

新增 2 项测试（重置清空游标且不动记录、运行中拒绝重置），全量 **38 类 285 项 0 失败**。

## 11.10 第五轮：报「账号或密码不正确」（2.3.44）

## 11.11 第六轮：把 LoTW 页面原话带进失败说明（2.3.45）

## 11.12 第七轮：作业卡在「进行中」不下来（2.3.46）

用户反馈：20:51:24 的作业一直显示「进行中」、拉取 0，点「重置游标」被拒（`QSL-409-LS-0001`「该配置已有一次同步在进行」），删除配置同样被挡。数据后来确实拉到了，但那条作业状态没有收尾，页面就一直停在「进行中」。

根因是三条叠加的：

1. **拉取挂在请求上**。`POST /log-sync/profiles/{name}/sync` 把整条同步链绑在 HTTP 请求里，LoTW 整份报表可能耗时数十秒；页面刷新会取消请求，链随之取消，收尾写入根本不会发生 → 作业永远停在 `RUNNING`。
2. **收尾写入本身也可能失败**。`finishJobWithError` / 完成分支直接 `client.update(job)`，一旦遇到乐观锁冲突就抛错，作业仍是 `RUNNING`。
3. **没有自救入口**。并发保护按「存在未结束作业」拒绝重置游标与删除配置，陈旧判定要等 10 分钟，重启插件也没有收尾逻辑。

2.3.46 的修改：

- `startSync()`：只等到作业创建成功就返回「任务已启动，稍后刷新作业表查看结果」，真正的 `executeSync` 在 `Schedulers.boundedElastic()` 上后台执行，客户端取消影响不到它。`runSync()` 保留同步语义供定时调度与测试使用。
- `saveJob()`：收尾写入失败时重新 `fetch` 最新作业再写，避免乐观锁冲突制造新的卡死。
- `forceStop()`：把该配置下所有 `RUNNING` 作业收尾为失败（说明写明「作业已被强制停止」），写审计「强制停止外部日志同步」，没有进行中作业时返回 `QSL-409-LS-0002`。端点 `POST /log-sync/profiles/{profileName}/force-stop`，前端在存在进行中作业时显示红色「强制停止」按钮。
- `reconcileRunningJobs()`：插件启动时把所有遗留 `RUNNING` 收尾为「作业执行被中断（插件重启或请求被取消）」。进程重启后不可能还有作业在跑，持久化状态却不会自己变——不收尾就会永远挡住重置游标与删除配置。
- 定时调度器加 `subscribeOn(Schedulers.boundedElastic())`，避免阻塞式 HTTP 占住默认单线程调度器。
- 前端「立即同步」改为轮询作业表（每 3 秒，最多约 2 分钟）直到没有 `RUNNING`，不再等接口返回统计值；`onUnmounted` 清理计时器。
- RBAC：`qsl-management-log-sync-edit` 对 `qso-records`/`log-sync-profiles`/`log-sync-jobs` 增加 `update` 动词（强制停止要写作业与配置）。

验证：新增 `QslLogSyncStuckJobTest` 5 项（强制停止收尾并写审计、无进行中作业返回 409、启动收尾遗留作业且不动已完成作业、已有进行中作业时拒绝发起新同步、陈旧 `RUNNING` 不再阻塞），`QslManagementPluginTest` 增加启动收尾断言；全量 **39 类 292 项 0 失败**，前端类型检查与 28 项前端测试通过。

## 11.13 第八轮：LoTW 限流（503 Page Request Limit）（2.3.47）

用户贴出失败说明：`LoTW 返回状态码 503（HTTP 503，text/html，396 字节，开头：<TITLE>Error 503</TITLE> … <B>Page Request Limit!</B> Only one page request per user at …`。

这是上游限流，不是凭据或网络问题：LoTW 对同一用户同时只允许一个报表下载，前一次没收完、或者连着点了「测试连接」再加「立即同步」，就会吃 503。

改了三处：

1. **识别**（`QslLotwLogSyncSource.looksLikeRequestLimit()`）：按 `Page Request Limit` / `one page request per user` / `request limit` 匹配正文，不看状态码——前置代理可能把状态码改成 200。命中报 `QSL-429-LS-0001`，文案说明「限制同一账号每分钟一次」，并带出上游页面原文。
2. **限流重试**：命中 429/503 后等 65 秒重试一次（上游写的是「等一分钟」），仍被拒才上报。等待时长抽成构造参数，测试不必真的等。
3. **账号级闸门**（`QslLogSyncService.ensureRequestInterval()`）：适配器声明 `minRequestIntervalSeconds()`（LoTW 60，QRZ 0），同步、连通性测试、定时任务共用同一张 `lastRequestAt` 表，间隔未到直接报 `QSL-429-LS-0002` 并说明还差几秒。

顺带修一个真缺陷：LoTW 的登录名原来取的是 `spec.myCallSign`，而页面让人填的是「账号（LoTW 用户名）」，官方明确「用户名多数等于主呼号但不总是如此」。现在优先用配置的账号，留空才回落到呼号（`resolveLoginName()`）。

另有健壮性修正：`describeBody()` 取 `response.headers()` 时不再假定非 null，诊断路径不能因为拿不到内容类型就抛 NPE 把真正的失败原因盖掉。
