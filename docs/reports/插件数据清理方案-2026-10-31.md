# 插件数据存放位置与清理方案

> 版本：2026-10-31（对应插件 2.3.47）。本文所有条目都基于仓库代码核对；涉及 Halo 侧表名的部分标注了核对方式，不靠记忆断言。
>
> 2026-10-31 修订：新增档案 E（恢复出厂）与第 2.5 节脚本批量清空 `scripts/clear-plugin-data.ps1`；订正第 3 节 `apiVersion` 判定语句（原文多了一层无意义的 `->> 0`）；补充 Secret 查询与全清语句。

## 1. 数据存在哪

这套插件**自己不落任何文件**。抓取、解析、导出全部在内存里完成（导出走 `ByteArrayOutputStream` 直接成为下载响应），所以「插件数据」全部落在四处：

| 位置 | 内容 | 说明 |
| --- | --- | --- |
| Halo 数据库的扩展存储表 | 20 种自定义扩展的全部实例（通联、卡片、地址、审计、作业、同步配置等） | 由 `QslExtensionSchemeRegistrar` 注册，group `qsl-management.bi1kbu.com`、version `v1alpha1` |
| Halo 数据库的 Secret 表 | 三类凭据：AI Key、QRZ 账号、外部日志同步账号密码 | 明文只在这里，配置里只存名字 |
| Halo 附件库（本地 `upload/` 或对象存储） | `StationCard.spec.imageAttachmentName` 指向的卡片图片 | 删扩展实例**不会**删附件，要单独清理 |
| 浏览器 localStorage | 8 个通联导出参数键，前缀 `qsl:qso-record:` | 只影响导出表单的默认值，与业务数据无关 |

### 1.1 二十个扩展类型（按 plural 定位）

| plural | 中文 | 体量级 | 清理建议 |
| --- | --- | --- | --- |
| `qso-records` | 通联记录 | 最大，通常上千 | 备份后再删 |
| `card-records` | 卡片记录 | 大 | 备份后再删 |
| `station-cards` | 卡片版本/制卡 | 中 | 保留（配置类） |
| `receive-records` | 收卡记录 | 中 | 备份后再删 |
| `offline-exchange-cards` | 线下换卡卡 | 中 | 备份后再删 |
| `exchange-requests` | 换卡申请 | 中 | 备份后再删 |
| `qsl-card-requests` | 实体卡申请 | 中 | 备份后再删 |
| `qsl-card-request-qso-reservations` | 申请占用的通联 | 小，随申请产生 | 随申请一起删 |
| `qsl-audit-logs` | 审计日志 | 持续增长，最容易堆 | 定期按时间清理 |
| `import-export-jobs` | 导入导出作业 | 中 | 可整表清 |
| `log-sync-jobs` | 外部日志同步作业 | 中，每次同步一条 | 可整表清 |
| `log-sync-profiles` | 外部日志同步配置 | 小 | 删前先停自动同步 |
| `address-book-entries` | 地址簿 | 小 | 配置类，保留 |
| `bureau-entries` | 卡片局 | 小 | 配置类，保留 |
| `equipment-catalog-entries` | 设备库 | 小 | 配置类，保留 |
| `station-equipments` | 本台设备 | 小 | 配置类，保留 |
| `station-profiles` | 本台资料（含本台呼号） | 单条 | **不要删**，删了呼号回落 BI1KBU |
| `system-setting`（单例 `qsl-system-setting-default`） | 系统参数 | 单条 | **不要删**，删了插件启动重建为默认值 |
| `qsl-migration-state`（单例） | 迁移状态 | 单条 | **不要删**，删了会按当前版本重建，历史迁移痕迹丢失 |
| `offline-activities` | 线下活动 | 小 | 配置类，保留 |

### 1.2 凭据（Secret 表）

| Secret 名 | 用途 | 生成方式 |
| --- | --- | --- |
| `qsl-log-sync-credential-<配置名>` | 外部日志同步账号与密码/Key | 由配置名派生，删除配置时连带删除 |
| `qsl-ai-openai-api-key`（可改） | AI 地址整理与导入解析 | `SystemSetting.spec.aiSecretName` 指过来 |
| `qrzComSecretName` / `qrzCnSecretName` 指向的名字 | QRZ 查址账号 | 同上，配置里只存名字 |

> 用 ⚠️ 记住一条：**删配置不等于删 Secret 的历史残留**。2.3.39 之前的版本把 Secret 名记在 `spec.credentialSecretName`，旧数据可能留下无主 Secret；2.3.39 起改为按配置名派生，删配置会连带删 Secret。

### 1.3 浏览器端

`qsl:qso-record:adif-my-sig`、`qsl:qso-record:adif-my-sig-info`、`qsl:qso-record:cabrillo-contest`、`qsl:qso-record:cabrillo-operators`、`qsl:qso-record:cabrillo-category-operator`、`qsl:qso-record:cabrillo-category-band`、`qsl:qso-record:cabrillo-category-mode`、`qsl:qso-record:cabrillo-category-power`。

清理：浏览器控制台执行 `Object.keys(localStorage).filter(k => k.startsWith('qsl:')).forEach(k => localStorage.removeItem(k))`。

## 2. 清理方案（按力度从轻到重）

### 档案 A：只清「痕迹」，不动业务（推荐日常用）

适用于「作业表、审计日志越积越多」。

1. 外部日志同步 → 作业表逐条删除，或按配置整体清（删除配置会连带清掉该配置的所有作业与凭据）。
2. 审计 → 报告审计模块按时间筛出旧日志后删除。
3. 数据 → 导入导出 → 历史作业清理。

接口层等价操作：

```bash
# 清某个同步配置（连带凭据与该配置的历史作业）
curl -X DELETE -b "Cookie: <控制台会话>" \
  "http://<站点>/apis/console.api.qsl-management.bi1kbu.com/v1alpha1/log-sync/profiles/<配置名>"
```

### 档案 B：清业务数据，保留配置

适用于「想从零开始录入，但保留呼号、参数、地址簿、卡片版本」。

删这些：`qso-records`、`card-records`、`receive-records`、`offline-exchange-cards`、`exchange-requests`、`qsl-card-requests`、`qsl-card-request-qso-reservations`、`import-export-jobs`、`log-sync-jobs`。

保留这些：`station-profiles`、`system-setting`、`station-cards`、`bureau-entries`、`address-book-entries`、`equipment-catalog-entries`、`station-equipments`、`offline-activities`、`log-sync-profiles`、`qsl-migration-state`。

### 档案 C：清空插件全部数据（保留插件本体）

在档案 B 基础上再删：`qsl-audit-logs`、`log-sync-profiles`（连带 Secret）、所有 `imageAttachmentName` 指向的附件。`station-profiles` 与 `system-setting` 留着，插件照样能跑；想连本台呼号一起重置，删掉 `station-profiles` 后重启插件会重建默认资料（呼号回落 BI1KBU）。

### 档案 D：彻底卸载重置

1. 控制台「插件」→ 卸载 `qsl-management`。Halo 卸载插件**不会**自动清除该插件的自定义扩展实例，数据仍在库里。
2. 若确实要连数据一起清：按档案 C 删完再卸载，或卸载后按第 3 节直连数据库清理。
3. 重装后 `SystemSetting`、`StationProfile`、`QslMigrationState` 会自动重建，作业与同步配置为空。

### 档案 E：恢复出厂（清空全部 + 重启重建默认）

「清空插件所有数据」就是这一档，等价于把插件恢复到刚装上的样子。

**做法**：把 20 类扩展实例全删 → 清凭据 → 清卡片图片附件 → 清 localStorage → 重启插件/Halo。

重启后插件启动链会自己补齐三件默认资源（`QslManagementPlugin.start()` → `ensureDefaultResources` + `ensureMigrationState`）：

| 删掉的东西 | 重启后会怎样 |
| --- | --- |
| `system-settings`（`qsl-system-setting-default`） | 重建为默认值：访客 30 次/分钟、换卡冷却 5 分钟、卡号起始 1000、AI/QRZ 全关 |
| `station-profiles`（`qsl-station-profile-default`） | 重建默认资料，**本台呼号回落示例值 BI1KBU**，要重新填 |
| `qsl-migration-states` | 按当前插件版本重建，历史迁移痕迹丢失（数据已清空，无影响） |
| 其余 17 类 | 不重建，就是空的 |

推荐用脚本做（见第 2.5 节），不要手写循环。

## 2.5 脚本批量清空（推荐，不停站、不碰数据库）

仓库里有两个等价脚本，按运行环境选一个：

| 脚本 | 环境 |
| --- | --- |
| `scripts/clear-plugin-data.sh` | Linux / macOS / WSL，以及 **Ubuntu 服务器上的 Docker 部署（推荐）** |
| `scripts/clear-plugin-data.ps1` | Windows PowerShell |

两者都走 Halo 的扩展 CRUD 接口逐条删除，Halo 自己维护索引，因此**不需要停机、不需要登录数据库**。

**第一步：拿个人令牌**。控制台右上角头像 → 个人中心 → 个人令牌 → 新建，得到 `pat_` 开头的字符串（[Halo 官方说明](https://docs.halo.run/2.23/developer-guide/restful-api/introduction)）。用超管身份建，因为删除需要对应资源的 delete 权限。

### 2.5.1 Ubuntu / Docker（bash 脚本）

Halo 跑在 Docker 里时，**在宿主机跑脚本**，用映射出来的端口（`-p 8090:8090` 就是默认的 `http://127.0.0.1:8090`）。脚本只需要 `curl` 和 `python3`（Ubuntu 默认都有）。

```bash
# 先看会删多少条（不删）
TOKEN=pat_xxx ./scripts/clear-plugin-data.sh --dry-run

# 只清业务数据（通联、卡片、收卡、换卡、申请、作业、审计），保留全部配置
TOKEN=pat_xxx ./scripts/clear-plugin-data.sh

# 清空全部（含配置类），即恢复出厂
TOKEN=pat_xxx ./scripts/clear-plugin-data.sh --scope all

# 站点不在本机 8090 时
BASE_URL=http://10.0.0.5:8090 TOKEN=pat_xxx ./scripts/clear-plugin-data.sh --scope all
```

脚本会先打印「类型 / 清理前 / 已删除」表格，再逐类型清空；`-` 开头参数为 `--dry-run`、`--scope business|all`、`--help`。

### 2.5.2 Windows（PowerShell 脚本）

```powershell
.\scripts\clear-plugin-data.ps1 -Token pat_xxx -DryRun
.\scripts\clear-plugin-data.ps1 -BaseUrl http://localhost:8090 -Token pat_xxx
.\scripts\clear-plugin-data.ps1 -BaseUrl http://localhost:8090 -Token pat_xxx -Scope all
```

### 2.5.3 两个脚本的共同行为

- `--scope all`（或 `-Scope all`）在业务数据之外，额外清掉 `log-sync-profiles`、`station-cards`、`address-book-entries`、`bureau-entries`、`equipment-catalog-entries`、`station-equipments`、`offline-activities`、`station-profiles`、`system-settings`、`qsl-migration-states`。
- 每类先 `GET ?page=0&size=100` 取一页、逐条 `DELETE`，删完再取，直到该类型为空；单类超过 1000 轮会主动停下并告警，避免异常死循环。
- 删除 `log-sync-profiles` 时插件会连带删除该配置的凭据 Secret 与历史作业（`QslLogSyncService.deleteProfile`），所以凭据不用另外处理。
- 收尾会提示还要手工清的三处（附件、localStorage、重启重建默认值）。

**不改脚本也能手工清**：控制台逐页全选删除也能达到同样效果，只是上千条记录会点很久。

## 3. 直连数据库清理（最后手段）

**前置条件**：先停 Halo 进程（Halo 的查询索引在内存里，运行中直改库会让页面看到旧数据直到重启）；先做整库备份。

```bash
# PostgreSQL
pg_dump -Fc -d halo > halo-backup-$(date +%F).dump
# MySQL
mysqldump --single-transaction halo > halo-backup-$(date +%F).sql
```

**先摸清表结构**（不同 Halo 版本表名/列名可能不同，不要照抄猜测）：

```sql
-- PostgreSQL：\dt 或
SELECT table_name FROM information_schema.tables WHERE table_schema = 'public' ORDER BY 1;
-- MySQL
SHOW TABLES;
```

Halo 2 的扩展实例集中在扩展存储表（通常名 `extensions`，含一列存放扩展 JSON），Secret 在 `secrets` 表。**用下面这条先确认再删**（PostgreSQL 示例，`data` 列名以实际为准）：

```sql
-- 0) 先看清表结构，别照抄列名（PG）
\d extensions
-- MySQL: SHOW CREATE TABLE extensions\G
```

```sql
-- 1) 先数一遍，确认范围
SELECT count(*) FROM extensions
WHERE data::jsonb ->> 'apiVersion' LIKE 'qsl-management.bi1kbu.com/%';
```

```sql
-- 2) 按类型统计分布（确认哪些多、哪些少）
SELECT (data::jsonb ->> 'kind') AS kind, count(*)
FROM extensions
WHERE data::jsonb ->> 'apiVersion' LIKE 'qsl-management.bi1kbu.com/%'
GROUP BY 1 ORDER BY 2 DESC;
```

```sql
-- 3) 备份要删的行（做完 1、2 再执行）
\copy (SELECT * FROM extensions WHERE data::jsonb ->> 'kind' IN ('QsoRecord','CardRecord','ReceiveRecord','OfflineExchangeCard','ExchangeRequest','QslCardRequest','QslCardRequestQsoReservation','ImportExportJob','LogSyncJob')) TO 'qsl-rows.csv' CSV HEADER
```

```sql
-- 4) 删除（按档案 B 的范围，逐个 kind 走，别一条大语句全清）
DELETE FROM extensions WHERE data::jsonb ->> 'kind' = 'QsoRecord';
```

**要清空全部（档案 E）** 时不必逐个 kind，一条就够，且比逐个删更难漏：

```sql
-- 全清本插件 20 类扩展（含配置类），重启后 system-settings / station-profiles / qsl-migration-states 自动重建
DELETE FROM extensions WHERE data::jsonb ->> 'apiVersion' LIKE 'qsl-management.bi1kbu.com/%';
-- 回看结果，应为 0
SELECT count(*) FROM extensions WHERE data::jsonb ->> 'apiVersion' LIKE 'qsl-management.bi1kbu.com/%';
```

MySQL 把 `data::jsonb ->> 'kind'` 换成 `JSON_UNQUOTE(JSON_EXTRACT(data, '$.kind'))`，`apiVersion` 同理换成 `JSON_UNQUOTE(JSON_EXTRACT(data, '$.apiVersion'))`。

Secret：

```sql
-- 先看清有哪些（AI/QRZ 的 Secret 名可自定义，不要凭猜删）
SELECT name FROM secrets WHERE name LIKE 'qsl-%' OR name LIKE 'qrz%' OR name LIKE '%openai%';

-- 外部日志同步的凭据按固定前缀派生，可以直接删
DELETE FROM secrets WHERE name LIKE 'qsl-log-sync-credential-%';
```

> AI Key 与 QRZ 账号的 Secret 名记在 `SystemSetting.spec`（`aiSecretName` / `qrzComSecretName` / `qrzCnSecretName`）。若把 `system-settings` 也删了，这三条 Secret 就失去引用，属于无主残留——功能上无害，但要彻底清就按上面第一条查出名字再删。

> 删完必须重启 Halo，让它按现有行重建查询索引；否则控制台仍会显示已经删掉的数据。

## 4. 清理顺序（别打乱）

1. 外部日志同步 → 关掉「启用自动同步」，避免清理过程中又写回数据。
2. 若作业表有「进行中」，先点「强制停止」（2.3.46 起提供）。
3. 导出备份：数据 → 导入导出 → 选数据集导出（这是唯一能原样导回业务数据的路径）。
4. 按档案删数据。
5. 清附件（卡片图片）与浏览器 localStorage。
6. 重启 Halo，确认控制台各页面为空但可正常新建。

## 5. 风险清单

| 操作 | 后果 |
| --- | --- |
| 删 `station-profiles` | 本台呼号回落 BI1KBU，所有页面的呼号示例、制卡签发地址绑定都跟着变 |
| 删 `system-setting` | 参数全部回默认（含卡号起始 1000、访客限流 30/分钟、换卡冷却 5 分钟） |
| 删 `qsl-migration-state` | 迁移状态按当前版本重建，历史迁移痕迹丢失，跨版本升级时无法判断是否已迁移 |
| 删 `station-cards` | 制卡签发的卡片版本消失，历史卡片记录会指向不存在的版本 |
| 删 `card-records` 但留 `receive-records` | 收卡记录指向的卡片记录不存在，收卡查询页会显示空关联 |
| 直改库不重启 Halo | 页面继续显示已删数据，新建时可能出现重名冲突 |
| 卸载插件 | 不清数据；重装后旧数据仍在，属于「以为清了其实没清」 |

## 6. 验证

清理后逐页确认：总览统计归零、通联记录空、卡片记录空、审计日志空、外部日志同步配置与作业空、参数页仍是你的值（或默认值）、本台呼号仍是你的呼号。再点一次「外部日志同步 → 测试连接」确认凭据已清（应提示账号或密码未配置）。
