- 卡片类型 `cardType`：`QSO / SWL / EYEBALL`；发卡异常时写 `原类型（ERROR）`。
- 邮件策略 `*MailPolicy`：`AUTO_SKIP / MANUAL / AUTO_SEND`；线上换卡策略 `onlineExchangeRequestPolicy`：`DISABLED / MANUAL / AUTO_APPROVE`。
- 迁移状态：`BOOTSTRAPPED / PENDING / SUCCESS`；迁移类型 `AUTOMATIC / MANUAL`；当前 `dataSchemaVersion = "2"`。

**内置特殊值（改动时最容易踩）**：
1. 卡片版本「不发卡」不入 `StationCard`，库存无限，不进制卡/发信/统计链路，但收卡必须能关联。
2. 占位记录 `NC{n}` 不得出现在制卡/发信/送达列表，前台编号空白。
3. 内置线下活动「日常线下换卡」不入 `OfflineActivity`，但后台清单、建卡、收卡、公开页都要展示。

## 5. 六条业务主线

1. **通联业务**：QsoRecord（含 ADIF/Cabrillo 导入导出）→ 创建卡片（必须选版本，可选「不发卡」）→ 制卡签发（含地址绑定）→ 发信确认 → 送达确认。
2. **实体 QSL 卡申请**：匿名 `/qsl_card` 查 QSO → 逐条 QSO 选卡片版本 → 提交申请（写 `QslCardRequest` + QSO 占用）→ 后台审核 → 通过即逐条建 `CardRecord`（部分失败可幂等重试）→ 制卡/打包/发卡/签收状态公开回显。
3. **线上换卡**：匿名提交 `ExchangeRequest`（限流 + 冷却 + 同呼号待审核拒绝）→ 后台审核（通过不自动建卡，需显式点「创建卡片」）→ 后端复用制卡/发信组件 → 签收确认（`CardRecord.spec.receiptConfirmed`）。
4. **线下换卡**：`OfflineActivity` → 建卡（允许空呼号，不绑地址）→ 制卡 → 送达确认（公开页 `/eyeball` 回写 `cardSent`）。
5. **收卡业务**：先建 `ReceiveRecord`，再尝试关联发卡记录，匹配不到保留 `matchStatus=未匹配`；人工「关联卡片」可补；收卡编号迁移只在批量编辑页签。
6. **审计与数据**：只读查询 + 统计报表；写操作全部落 `QslAuditLog`；数据页含卡片异动（重发/发卡异常）、地址/卡片局/设备库、导入导出、旧版迁移。

状态机联动铁律（`documented` §3.7.4）：`cardSent=true` 会补齐 `cardIssued/cardIssuedAt/envelopePrinted`；线上换卡「已签收」在未制卡/未打包/未发卡时同样补齐；状态被改回否/空时，对应时间、邮件状态、邮件时间、邮件错误同步置空。

## 8. 权限与菜单

- 权限节点命名：`plugin:qsl-management:<节点>:view` / `:edit`，落在 `qsl-menu-role-templates.yaml`（40 个 Role；含 `card-print-tool:use`、两个 `aggregate-to-anonymous` 聚合角色 `qsl-management-public-view` / `qsl-management-public-submit`）。
- 权限 key 的唯一事实源是 `menu/MenuModuleRegistry.java:9-111`（17 个模块）+ `ui/src/constants/menu-modules.ts`；两者必须与 yaml 的 `ui-permissions` 三处对齐。
- 服务端 RBAC 是安全边界；前端权限隐藏只是体验。`edit` 依赖对应 `view`，通过 `rbac.authorization.halo.run/dependencies` 表达。

### 控制台鉴权的真实机制（`observed`，改路由前必读）

`QslConsoleApiEndpoint.java:789-802` 的 `ensureAuthenticated()` **只判断「是否登录」**（`principal` 存在且不是 `anonymousUser`），否则抛 `QSL-401-0001`。**细粒度权限 100% 由 Halo RBAC 按「apiGroup + 路径首段资源 + 方法动词」判定**，规则来自 yaml。推论：

> 新增一条控制台路由时，如果忘了在 yaml 里给对应资源加 verbs，这条路由对**所有角色**都 403，而且不会有任何编译或测试失败提示。`QslRoleTemplateContractTest` 是唯一的护栏，但它靠手写断言，没写进断言的路由就等于没保护。

### ⚠ 本次发现的不一致（`observed`，两处，均已交叉核对）

**发现 A：权限节点 `card-issue` 无角色模板。**

前端 `ui/src/constants/menu-modules.ts:125` 与后端 `MenuModuleRegistry.java:47` 都引用 `plugin:qsl-management:card-issue:view/edit`（通联/线上/线下三个「制卡签发」菜单），但全文 grep `qsl-menu-role-templates.yaml` 中 `card-issue` **零命中**。
影响（`inferred`）：超管不受影响；一旦给非超管角色按模板授权，三个「制卡签发」菜单会因缺 `card-issue:view` 而不可见。同时 `ProductDefinition.md` §5.3 把 `card-issue` 列为正式权限节点，文档与模板不符。

**发现 B：控制台路由 `/receipt-confirms/{cardRecordName}/confirm` 无任何授权。**

`QslConsoleApiEndpoint.java:124` 声明该路由，但 yaml 中 `receipt-confirms` **零命中**（已用脚本把代码里 42 条路由的 20 个首段资源与 yaml 的 `console.api` 资源全集做差集，唯一缺口就是它）。
影响（`inferred`）：该路由在 RBAC 下对一切角色 403，等同死路由。实际签收走 `mail-receive-confirms` 与控制台外的公开 `/receipt-public/-/confirm`。

**处置建议（两处同病）**：要么补 Role 模板/资源规则，要么从代码与文档里删掉。**改前先确认哪一种才是设计意图**；顺手把这两个缺口写进 `QslRoleTemplateContractTest` 的断言，防止再次漂移。
