# QSL 项目信息结构化清单

更新时间：2026-10-17

代码核验范围：`插件工程根目录`、`tools/CardPrint`

## 1. 项目定位
1. 项目名称：QSL 管理系统（Halo2 插件 + 本地打印工具）。
2. 核心目标：围绕通联、换卡、制卡签发、发信与送达确认、收卡编号管理，提供可持久化的后台业务流与前台自助页面。
3. 技术形态：
   - Halo2 插件后端：Java 21 + Spring WebFlux + Halo Extension API
   - Halo2 插件前端：Vue 3 + TypeScript
   - 本地打印工具：`tools/CardPrint`（Python）

## 2. 仓库结构
1. `src/`：Halo2 插件后端、扩展模型、资源清单与权限模板。
2. `ui/`：Halo2 控制台前端工程。
3. `tools/CardPrint/`：本地在线打印工具（独立 Python 项目）。
4. `docs/spec/`：结构化项目信息文档。
5. `docs/spec/ProductDefinition.md`：产品定义（约束性文档）。
6. `docs/spec/BackendApiContract.md`：后端 API 合同（输出性文档，需与代码同步）。
7. `docs/spec/Halo非资源型API待核查问题.md`：深层自定义 API 的 Halo RBAC 分类与权限匹配待核查记录。
8. `agents.md`：协作与约束规则（约束性文档）。
9. `docs/plans/实体QSL卡申请开发约束框架.md`：`/qsl_card` 实体 QSL 卡申请功能的约束性开发框架，当前功能已按该框架实现。

## 3. 后端架构（src/main/java）
1. 插件启动与默认资源：
   - `QslManagementPlugin`：确保默认 `SystemSetting`、`StationProfile` 和 `QslMigrationState` 实例存在，并在迁移状态确认后修复实体卡申请的孤立 QSO 占用。
2. Extension 注册：
   - `QslExtensionSchemeRegistrar`：注册并维护名称索引。
3. 业务服务：
   - `QslConsoleActionService`：后台业务操作（确认、状态流转等）。
   - `QslImportExportJobService`：导入导出任务。
   - `QslNotificationMailService`：邮件发送与状态记录。
   - `QslAiService`：AI 配置测试、OpenAI 兼容协议调用、线上换卡导入 AI 解析、地址整理与 QRZ 呼号地址解析。
   - `QslQrzAddressLookupService`：QRZ.COM 官方 XML 查询、QRZ.CN 页面抓取与主体预处理、Secret 凭据写入与地址预览。
   - `QslPublicApiService`：前台公开业务处理。
   - `QslCardRequestService`：实体 QSL 卡申请查询、提交、地址绑定、QSO 占用、审核、自动建卡、重试与启动恢复。
4. Endpoint 分层：
   - `console.api.qsl-management.bi1kbu.com`：控制台 API
   - `api.qsl-management.bi1kbu.com`：公开 API 与前台页面路由
   - 部分深层自定义路由超过 Halo 官方资源型 API 的 `resource/resourceName/subresource` 结构，其 RBAC 分类和普通角色权限命中情况尚待运行验证，详见 `docs/spec/Halo非资源型API待核查问题.md`；该记录当前不代表已确认缺陷。
5. 前台渲染与短码：
   - `QslPublic*PageRenderService`：前台页面 HTML 渲染
   - `Qsl*EmbedContentTransformer`：文章/页面短码转嵌入卡片

## 4. 前端架构（ui/src）
1. 入口：

2. 菜单配置：
   - `constants/menu-modules.ts`：模块定义、权限节点、依赖关系。
3. 模块承载：

5. 业务页面：

### 呼号示例数据流（2026-10-13）

- 唯一持久化来源：`StationProfile` 单例 `qsl-station-profile-default` 的 `spec.myCallSign（本台呼号）`，缺失或空白时使用 `BI1KBU`。
- 后台通联日志、创建卡片、发信确认、卡片异动（含批量字段）通过 `GET /apis/api.qsl-management.bi1kbu.com/v1alpha1/station-call-sign` 读取 `callSign（本台示例呼号）`；通信地址页面自身的示例保留默认值，保存成功后刷新共享示例。
- 公开查询、实体卡申请、线上换卡、线下换卡、公开签收的占位呼号在页面渲染时读取同一来源并进行 HTML 转义。仅示例使用配置呼号，URL 预填呼号与实际业务输入保持各自语义。
- 新增接口允许匿名限流读取，仅返回呼号；不开放完整通信地址的匿名读取或写入权限，不改变菜单、Extension 字段及迁移状态。
- CardPrint 的“补打眼球卡片”通过既有“登录并拉取卡片版本”后台任务读取通信地址中的呼号，在主线程更新占位文字；切换站点后先恢复默认示例，忽略旧站点的迟到响应。单纯加载本地配置不会额外发起网络请求，更新远程呼号后需重新拉取资料。桥接方法 `fetch_station_sender` 的返回字典新增 `my_call_sign（本台示例呼号）`，其余寄件信息与实际打印输入保持原语义。

### 制卡签发地址绑定（2026-10-17）

- “确认打包”仅将当前卡片的 `envelopePrinted（打包状态）` 设为真并推进流转状态，原地址和邮箱保持原值，空地址也不自动补齐。
- 地址候选不会直接保存；页面列出目标卡片编号后，由“确认绑定地址”显式提交。目标呼号精确匹配，并排除已打包、已发出或已签收的卡片；个人地址、代理收件地址和卡片局都通过此流程绑定。
- 每次提交固定候选地址、目标卡片和 `metadata.version（资源版本）`；写入期间锁定页面操作，失败立即停止后续记录并报告已保存数量。切换查询上下文时清空候选，防止串用地址。
- 使用既有 Extension `PUT /apis/qsl-management.bi1kbu.com/v1alpha1/card-records/{name}` 与既有审计、邮件策略 API，无路由、权限、数据模型或 CardPrint 契约变更，不执行历史数据迁移或补发邮件。

## 6. 核心数据模型（Extension）
1. `SystemSetting`：系统参数（限流、审核开关、序号等）。
2. `StationProfile`：本台通信地址与联系信息。
3. `StationEquipment`：本台设备信息。
4. `StationCard`：本台卡片版本、库存、排序与 Halo 附件库图片引用；后台通过图片选择入口打开附件库弹窗，在弹窗内上传或选择图片后写入附件引用；卡片图案原图不写入本资源，旧版 `imageUrl` base64 字段不再兼容，后台不再提供旧图片字段清理入口。`status.active=true` 表示该版本仅支持实体 QSL 卡申请、普通通联和线下换卡，线上换卡页面仍展示但不可选择；`false/null` 表示全部业务均可使用，新建版本默认关闭该限制。系统内置卡片版本“不发卡”不保存为 `StationCard`，仅在卡片版本选择器中作为特殊选项存在，库存视为无限，不显示在“配置-本台卡片”菜单中；发送链路页面隐藏该类记录，收卡业务仍显示并允许关联。
5. `QsoRecord`：通联日志。
6. `CardRecord`：卡片主记录（场景、版本、状态、备注、邮件状态、地址绑定、签收状态）。线下换卡卡片不绑定地址；线上换卡“送达确认”语义为确认签收/签收状态，签收事实为 `CardRecord.spec.receiptConfirmed`。
7. `ExchangeRequest`：线上换卡申请，状态区记录审核结果与审核通知邮件发送状态。
8. `OfflineActivity`：线下换卡活动。
9. `AddressBookEntry`：通信地址簿，保存呼号、姓名、电话、邮编、去向国、收件地址、邮箱与地址备注；去向国非必填。
10. `BureauEntry`：卡片局地址簿，保存卡片局名称、电话、邮编、去向国、地址与备注；去向国非必填。
11. `EquipmentCatalogEntry`：设备库。
12. `QslAuditLog`：审计日志。
13. `ImportExportJob`：导入导出任务。
14. `ReceiveRecord`：独立收卡事实，是收卡业务的收卡编号来源，记录收卡编号、呼号、卡片类型、来源场景、关联发卡记录与匹配状态。
15. `OfflineExchangeCard`：线下换卡活动卡，记录活动、待认领呼号、发出状态和线下备注。
16. `QslMigrationState`：插件数据版本与迁移状态单例，记录运行插件版本、最后一次数据状态确认成功的插件版本、数据模型版本、已执行迁移、待迁移项和最近迁移结果。
17. `QslCardRequest`：实体 QSL 卡申请，申请编号使用 `QCR{四位以上序号}`，保存呼号、逐条 QSO 与卡片版本、地址绑定、通知邮箱、备注、审核状态、建卡状态及 QSO 与卡片编号的一对一映射；公开页面的审核、制卡、打包、发卡和签收进度由申请与关联 `CardRecord` 实时聚合，不新增重复持久化状态。
18. `QslCardRequestQsoReservation`：实体卡申请 QSO 持久化占用，使用 QSO 编号哈希生成确定性资源名，防止同一 QSO 并发重复申请；拒绝、建卡成功或启动修复时释放无效占用。
19. `LogSyncProfile`：外部日志同步配置，记录数据源类型（LoTW / QRZ Logbook）、本台呼号、账号名、凭据 Secret 名、启用与自动同步开关、同步间隔、默认场景类型、重复记录处理策略与单次最多拉取条数；状态区记录最近同步时间、最近游标、最近错误与连续失败次数。密码只存 Halo `Secret`，不写入本资源。
20. `LogSyncJob`：外部日志同步作业，记录所属配置、数据源、呼号、触发方式、游标区间、最多拉取条数，以及拉取/新建/更新/跳过/失败条数、失败摘要与最多 200 条失败明细。

导入导出备份数据集覆盖 `qso-record/card-record/receive-record/exchange-request-review/qsl-card-request/qsl-card-request-qso-reservation/offline-activity/offline-exchange-card/address-management/bureau-management/equipment-catalog/system-setting/station-profile/station-equipment/station-card`；`all` 导出需同时包含业务数据、实体卡申请及有效 QSO 占用、收卡事实、线下换卡活动卡、线下换卡活动清单与配置菜单数据。导入导出前端识别 ZIP 内 CSV 时优先按 `id#数据集` 与文件名精确匹配，避免 `station-card.csv` 被宽泛 `card` 关键词误判为 `card-record`；服务端导入 `card-record` 时跳过 `qsl-station-card-*` 或 `station-card-*` 资源名，导出 `card-record` 时过滤此类历史脏记录。插件升级状态由 `QslMigrationState` 持久化，启动时刷新当前运行版本，数据模型版本 `2` 记录 `schema-2-qsl-card-request`，预检接口只计算待迁移项，不写入业务数据。2.0.0 前旧导出包需通过 `tools/convert_legacy_export_to_qsl2.py` 转换，转换时从旧卡片记录聚合提取收卡关联与线下活动卡关系，并过滤误进入 `card-record.csv` 的 `qsl-station-card-*` 本台卡片版本占位记录。导入导出页面提供“旧版本迁移”页签，用于 Halo 存储仍保留旧模型数据时原地迁移；执行前必须全量备份，并输入确认文字“确认迁移旧版本数据”。

关键新增字段事实：

1. `SystemSetting.spec` 包含 `guestQueryPerMinute/onlineExchangeRequestPolicy/onlineExchangeRequestCooldownMinutes/onlineAutoApprovedRequestMailPolicy/requiresExchangeReview/cardRecordSequence/receiveRecordSequence`，线上换卡页面收到表单的处理策略按 `DISABLED/MANUAL/AUTO_APPROVE` 保存，同呼号重复提交冷却时间默认 5 分钟且适用于待审核、已通过和已拒绝申请，系统自动审批通过后的本台邮件通知策略按 `AUTO_SKIP/AUTO_SEND` 保存，接收人为 `StationProfile.spec.myEmail`，`requiresExchangeReview` 作为历史兼容字段保留；邮件策略按业务拆分为 `qsoCardCreatedMailPolicy/qsoCardSentMailPolicy/qsoCardReceivedMailPolicy`、`onlineCardCreatedMailPolicy/onlineCardSentMailPolicy/onlineCardReceivedMailPolicy/onlineExchangeReviewedMailPolicy`，取值为 `AUTO_SKIP/MANUAL/AUTO_SEND`；业务动作触发自动策略时，`AUTO_SKIP` 在业务条件满足时写入对应邮件状态 `SKIPPED`，不触发 Halo 通知；`apply-policy` 对手动待处理或自动不发送（AUTO_SKIP）策略下条件不足返回 `PENDING`（仅响应值，不持久化），界面明确区分等待手动发送与已跳过；`offlineAutoNotifyOnCardReceived` 作为历史配置字段保留但不再使用，线下换卡收卡与送达确认默认不发送邮件；旧的全局自动通知字段和场景布尔字段仅作为已有配置读取兜底。AI 配置字段包含 `aiEnabled/aiProvider/aiBaseUrl/aiModel/aiSecretName/aiTemperature/aiTimeoutSeconds/aiMaxConcurrentRequests/aiMaxInputCharacters/aiOnlineImportParseEnabled/aiAddressCleanupEnabled/aiSystemPrompt/aiOnlineImportPrompt/aiAddressCleanupPrompt/aiCallbookAddressPrompt`，提示词为完整模板，配置页可查看、编辑并按项重置；`aiMaxConcurrentRequests` 默认 1、最大 10，用于服务端第三方 AI 调用并发排队控制；自定义提示词不允许改变系统指定 JSON 返回结构。QRZ 配置字段包含 `qrzComEnabled/qrzComUsername/qrzComSecretName/qrzComXmlBaseUrl/qrzCnEnabled/qrzCnUsername/qrzCnSecretName/qrzCnLookupUrlTemplate/qrzTimeoutSeconds`；服务端只允许 QRZ.COM / QRZ.CN 官方域名，QRZ 凭据测试通过后才写入配置与 Secret；QRZ.COM 默认同时获取官方 XML 与资料页，资料页 Biography/Detail 主体可用时以资料页正文为主、XML 为辅交给 AI，资料页不可用时才回退 XML，XML 只有国家、省份、州等宽泛行政区时不直接作为有效地址；QRZ.CN 抓取结果会在服务端优先使用用户名和密码登录获取 Cookie，再执行配置 URL 原样请求、表单查询、概率性搜索页重试、目标呼号有效性校验、编码解码、主体内容与图片文件名线索抽取；页面明确提示呼号不存在时直接返回不存在，不再调用 AI，未获取到有效目标呼号页面时明确报错。AI API Key、QRZ.COM 密码、QRZ.CN 密码与自动刷新 Cookie 写入 Halo `Secret`，不写入 `SystemSetting.spec` 明文字段。
2. `StationCard.spec` 包含库存与排序字段：`availableInventory/versionTotal/sortOrder`；`StationCard.status.active` 表示是否仅限实体 QSL 通联卡业务，`true` 为受限、`false/null` 为通用。
3. `QsoRecord.spec` 包含 `sceneType/myQth/operator`。
4. `CardRecord.spec` 包含 `sceneType/offlineActivityName/addressEntryName/businessRemarks/createdRemarks/sentRemarks/receivedRemarks/publicReceiptRemarks/cardIssued/envelopePrinted/receiptConfirmed/receivedRecordCodes` 以及三类邮件状态字段。其中 `receiptConfirmed` 表示线上换卡等发卡场景的确认签收事实；`receivedRecordCodes` 为待 2.1.x 版本移除的历史字段，2.0.7 起普通业务、查询、统计、导入导出和前端展示不再读写；线下换卡卡片不写入 `addressEntryName`；`cardVersion=不发卡` 作为系统内置特殊值仅用于标记无需发卡的卡片，不占用库存，也不计入待发和已发统计；线上换卡审核通过后不自动创建卡片，审核页“创建卡片”按钮和线上换卡导入创建的卡片默认 `cardRemarks` 为“期待与您空中相遇。\nLooking forward to meeting you on the air.”；通联业务创建卡片页下方待创建记录仅显示尚未创建卡片且未标记“不创建卡片”的 QSO/SWL 记录，页面默认不选中卡片版本，操作栏一键创建正式卡片前必须先人工选择卡片版本，用户可手动选择系统内置“不发卡”，业务备注为空，通联业务默认 `cardRemarks` 为“通联愉快，期待空中常见。\nNice QSO，Hope to catch you on the air often.”。
5. `ExchangeRequest.spec` 包含 `sceneType/cardVersion`；`ExchangeRequest.status` 包含 `reviewStatus/reviewReason/reviewedBy/reviewedAt`、审核通知邮件字段 `reviewMailStatus/reviewMailSentAt/reviewMailLastError/reviewMailTargetEmail`，以及建卡纠偏字段 `cardCreated/cardCreatedAt/cardCreatedBy/createdCardRecordName`。新建换卡申请资源名使用 `EX####` 递增格式。
6. `QslCardRequest.spec` 包含 `callSign/qsoItems/addressType/addressEntryName/notificationEmail/remarks/submittedAt`；`status` 包含独立的审核状态、卡片创建状态、逐条卡片映射和审核邮件状态。个人地址每次由前台重新填写，公开页面不读取历史地址；提交后服务端按呼号、姓名、电话、邮编、地址和邮箱完整匹配复用或创建 `AddressBookEntry`。卡片局沿用 `BureauEntry.metadata.name`，不新增业务编号。公开 QSO 查询根据该申请和关联 `CardRecord` 计算 `AVAILABLE/REJECTED_REAPPLY/REVIEW_PENDING/CARD_CREATING/CARD_CREATION_FAILED/CARD_PENDING_ISSUE/CARD_ISSUED/CARD_PACKED/CARD_SENT/CARD_SIGNED`，并返回中英状态文字；“已有卡片”仅作为无法关联申请来源的待制卡旧数据提示，“已收卡片”不进入实体卡寄送进度。

## 7. 场景主字段约定
1. `sceneType` 使用：`QSO`、`SWL`、`ONLINE_EYEBALL`、`EYEBALL`。
2. 通联业务：主场景 `QSO/SWL`。通联日志清单支持按呼号和通联日期范围筛选，日期范围按 `QsoRecord.spec.date` 做闭区间匹配，并影响当前筛选导出范围。通联日志提供 `ADIF格式导入`、`ADIF格式导出`、`Cabrillo格式导入` 与 `Cabrillo格式导出` 页签；手工新增记录默认使用 `UTC+8`，启用 UTC 实时填充、ADIF 导入与 Cabrillo 导入保留 `UTC`；导入页不新增后端 API，解析预览后通过现有 `QsoRecord` 创建能力写入记录，无法落入现有模型的 ADIF 字段、Cabrillo 头字段、比赛交换信息和 QSO 行扩展字段追加到备注；ADIF 导入兼容字段只在原对应字段缺失时启用：`GRIDSQUARE` 回填对方位置，`MY_GRIDSQUARE` 回填本台 QTH，`TX_PWR` 写入我台发射功率且缺失时才回落到设备默认功率；ADIF 导入预览默认跳过重复记录，本站导出的 `APP_QSLMS_RECORD_ID` 已存在时按本站记录编号判重，外部 ADIF 或缺少本站记录编号时按 `sceneType/callSign/date/time/timezone/myRigMode/freq` 组成业务键判重；“导入可用记录”只创建非重复记录，“覆盖导入”需二次确认，仅批量更新已匹配到现有资源名或业务判重键的重复记录；同一业务判重键下存在多条现有记录时全部覆盖更新，文件内部重复和无效记录不写入；导出已勾选记录或当前筛选结果，不改变 `QsoRecord` 数据。ADIF 和 Cabrillo 导出日期时间均按记录时区换算为 UTC，并兼容 `UTC+8/UTC+08:00/GMT+8/北京时间/Asia/Shanghai` 等等价时区写法；ADIF 3.1.7 导出分别提供 `ADI` 和 `ADX`：`ADI` 以普通 ASCII 说明文本开头，仅写入可打印 ASCII，含中文或其他非 ASCII 的字段整字段省略，多行值压平；`ADX` 使用 UTF-8 XML 和对应 `_INTL` 字段保留国际化文本；`USB/LSB` 统一导出为 `MODE=SSB` 与对应 `SUBMODE`。ADIF 导出仅在 `FREQ` 存在 ADIF `Number` 类型的 MHz 数值时写入频率，`{BAND} BAND` 占位按 ADIF 3.1.7 波段枚举写入 `BAND`，不写入非数值 `FREQ`，由导入保留到备注中的 `MY_STATE/STATE/GRIDSQUARE/MY_GRIDSQUARE/SIG/SIG_INFO/QSO_DATE_OFF/TIME_OFF` 等字段导出时恢复为独立 ADIF 字段；ADIF 导出页内支持 `MY_SIG` 下拉、`MY_SIG_INFO` 输入，本地持久化保存导出参数，`MY_SIG` 为空时显示为“不添加”，`OPERATOR` 导出时强制采用呼号，`TX_PWR` 导出时按 ADIF `Number` 类型规范化为瓦特数值；Cabrillo 导出页支持 `CONTEST/OPERATORS/CATEGORY-*` 配置，并生成 Cabrillo 3.0 文本文件。
3. 线上换卡业务：主场景 `ONLINE_EYEBALL`。
4. 线下换卡业务：主场景 `EYEBALL`。

## 8. 接口边界（按代码当前状态）
1. 控制台 API 前缀：
   - `/apis/console.api.qsl-management.bi1kbu.com/v1alpha1/...`
2. 公开 API 前缀：
   - `/apis/api.qsl-management.bi1kbu.com/v1alpha1/...`
3. 公开页面路由（示例）：
   - 查询卡片：`/cards/page`
   - 换卡（线上）：`/online_eyeball`、`/online_eyeball/{cardId}`
   - 换卡（线下）：`/eyeball`、`/eyeball/{cardId}`
   - 签收：`/receipt_public`、`/receipt_public/{cardId}`
   - 实体 QSL 卡申请：`/qsl_card`，仅允许基础路径和可选末尾 `/`，不创建资源型页面路由或极简别名；页面面向用户的文案采用中文在上、英文在下的双语布局，不展示内部 API 字段名。QSO 表格最右侧提供“申请此记录的卡片”按钮，可申请记录点击后激活左侧复选框并展开候选区，已勾选时按钮显示“已选择此记录”，不可申请记录按钮禁用。勾选 QSO 后在记录下方展开可视化卡片版本候选区，候选项使用正方形 `object-fit: contain` 预览框完整显示横版或竖版图片，右侧显示版本名称与剩余可用数量，每条 QSO 独立单选。
   - 极简别名：`/oe`、`/eb`、`/rp` 及各自的 `/{cardId}`，分别等价于上述线上换卡、线下换卡和签收推荐路径。
4. 三类推荐根路径及极简别名属于匿名只读非资源型 API，由 `QslPublicShortPathWebFilter` 内部改写到原 CustomEndpoint，复用现有页面渲染、限流和输入校验，不产生浏览器重定向。短码和 CardPrint 默认生成推荐路径。原 `/apis/api.qsl-management.bi1kbu.com/v1alpha1/EYEBALL`、`ONLINE_EYEBALL`、`receipt-public` 页面路由自 2.4.0 起弃用，计划 3.0.0 移除；删除前必须先让新路径直接调用公共页面处理服务，解除对旧路由的依赖。公开提交 API 不在本次弃用范围内。
5. 公开提交与查询路由：
   - `GET /qso-public/records`
   - `GET /qso-public/grids`：匿名返回通联记录中的对方四位网格清单，按 `QsoRecord.spec.qth` 识别 4/6/8 位 Maidenhead 网格，统一截取四位后聚合；地区文字、地址或混合 QTH 跳过，同一网格返回去重呼号集合，`detailLevel（详情级别）` 为完整时返回通联明细，为简略时只返回呼号清单。

说明：
1. 卡片路径模式下采用二次确认参数（如 `cs`）进行回填校验；不匹配时页面回填为空白。
2. 公开页面与公开提交 API 分离，页面用于展示与表单，提交落到 `/-/` 子路径接口。
3. 通联业务创建卡片的关联记录为必填；已正式创建卡片或已标记“不创建卡片”的记录不再进入候选列表。“不创建卡片”使用 `NC####` 递增资源名的占位 `CardRecord` 持久化，不占用正式卡片编号；前台卡片 ID 保持空白展示，占位记录可编辑转为正式卡片，也可删除后释放关联记录候选。通联日志清单允许对未被占用的单条 QSO 一键创建正式 `C####` 卡片，卡片版本必须由用户在通联业务创建卡片页手动选择，业务备注为空，卡片备注使用通联业务默认值。
4. 制卡签发、发信确认、送达确认只处理正式卡片编号为 `C{序号}` 的 `CardRecord`，不显示无编号占位记录；控制台发信和送达匹配也排除无编号占位记录。
5. 线下换卡业务不需要打包、制卡邮件流程和收件地址展示；线下换卡制卡签发页面只提供确认制卡，已制卡记录不再因未打包或未发送制卡邮件留在待制卡列表。
6. 线下换卡公开页面 HTML 不直接携带本站联系信息；只有 `POST /exchange-offline/-/confirm` 成功写入后才在响应中返回本站通信地址。
7. 前台线下换卡确认提交成功后同步写入 `CardRecord.spec.cardSent=true`，并在原发卡时间为空时补齐 `sentAt`，使线下换卡业务送达确认中的发卡状态显示为“是”；提交备注写入 `CardRecord.spec.publicReceiptRemarks`，后台线下换卡制卡签发、创建卡片历史详情、送达确认清单等备注查看位置必须展示该字段。线下换卡活动内置“日常线下换卡”，不写入 `OfflineActivity`，不约束活动地点、活动日期和活动时间，创建卡片时使用实时日期时间；后台活动清单、线下卡片创建、收卡活动选择和公开线下换卡确认活动列表均展示该内置活动。2.0.0 起，线下换卡收卡基本功能必须选择收卡归属活动，该选择同时联动过滤清单；服务端按活动、呼号和卡片类型优先绑定已有线下发卡记录，找不到时只创建 `ReceiveRecord`，不再自动创建临时收卡卡片或新发卡编号。
8. 线上换卡公开提交成功后返回本站通信地址用于寄送提示；同一呼号在上一条 `ONLINE_EYEBALL` 申请审核通过或拒绝前不能重复提交，且上一条申请已通过或已拒绝时仍必须等待 `onlineExchangeRequestCooldownMinutes` 指定的冷却期结束后才能再次提交。若系统参数 `onlineExchangeRequestPolicy=AUTO_APPROVE`，提交成功后由系统自动审批通过，审核说明固定为“系统自动审批通过”，但不自动创建卡片；若 `onlineAutoApprovedRequestMailPolicy=AUTO_SEND`，自动审批通过后向本台通信地址中的电子邮件发送通知；若为 `DISABLED`，公开提交接口拒绝接收新申请；人工审核同意时仅在已有说明为空且本次未填写时保持空说明。
9. 线上换卡公开卡片版本接口使用短缓存；Extension 查询短暂失败时，优先返回上一次成功读取的卡片版本列表，避免公开表单因一次后端查询抖动直接不可用。接口返回全部卡片版本，并使用 `qsoOnly` 标记 `StationCard.status.active=true` 的实体 QSL 通联卡专用版本；线上换卡页面展示但禁选该类版本，提交服务同步拒绝。接口只返回卡片预览缩略图地址，不返回附件原图或 base64 图片内容。
10. 收卡业务三个子菜单的基本功能“确认收信”和清单内“确认收卡”必须使用页面上方填写的收卡日期；未填写日期时前端弹窗提示且服务端拒绝提交，不再默认使用当前日期；该日期在本次浏览会话内按收卡子菜单记忆，提交后不清空。2.0.0 起，收卡确认创建 `ReceiveRecord`；收卡编号来源统一为 `ReceiveRecord.metadata.name`；匹配到发卡记录时写入关联关系，匹配不到时保留未匹配收卡记录，不再为收卡自动创建新的发卡卡片编号。同一发卡卡片 ID 可连续关联多条收卡事实，确认收卡只新增 `ReceiveRecord` 并保持本轮收卡打开，不触发收卡邮件自动策略，页面对已收但未结束的记录显示“继续收卡”和“结束收卡”；只有人工点击“结束收卡”进入回执处理状态后才关闭该发卡记录的继续收卡入口。收卡业务基本清单仍必须显示已结束收卡的发卡记录，但不再显示“继续收卡/结束收卡”入口。收卡业务三个子菜单的“已收卡片”页签在操作列提供“关联卡片”，允许把未关联发卡编号的收卡记录人工关联到同呼号、同卡片类型、同业务场景的正式发卡记录；线下换卡还需同活动，提交前必须二次确认，关联后服务端刷新目标卡片的已收状态。线上换卡收卡的已收卡片页签允许对未匹配且未关联发卡编号的收卡记录点击“创建卡片”，由服务端创建线上换卡正式卡片并写回匹配关系。收卡业务候选与清单必须包含 `cardVersion=不发卡` 的正式卡片，以便对方来卡事实可关联到无需我方发卡的通联记录。收卡业务“批量编辑”页签保留“迁移收卡编号”入口，用于将源卡片已关联的收卡编号迁移到同呼号、同卡片类型、同业务场景的目标发卡记录，并在服务端刷新源卡片与目标卡片的已收状态；通联业务“送达确认”不再显示该入口。
11. 状态流转联动：线下换卡收到对方“已签收”时补齐未完成的 `cardSent/sentAt`；线上换卡“送达确认”语义调整为确认签收/签收状态，签收事实写入 `CardRecord.spec.receiptConfirmed`，不代表我方收到对方卡片；线上换卡收到对方“已签收”时补齐未完成的 `cardIssued/cardIssuedAt/envelopePrinted/cardSent/sentAt`；通联业务和线上换卡业务只要 `cardSent=true`，即联动补齐制卡和打包状态。批量编辑将状态机改为否或空时，对应时间、邮件状态、邮件时间和邮件错误字段同步置空。线上换卡审核通过只代表申请通过和我方待发卡，不代表我方已收到对方卡片。普通业务、公开查询、审计页面与统计展示、筛选和排序“已收”时，以 `CardRecord.status.flowStatus=已收卡片` 为依据，`CardRecord.spec.cardReceived` 只作为后台状态维护字段；`ReceiveRecord.spec.outboundCardNames` 是状态机输入事实，只要卡片存在收卡记录关联，即必须刷新为“已收卡片”；导入忽略外部 `flowStatus` 并在导入完成后重建卡片状态机。
12. 总览看板与统计报表的卡片类统计项只统计正式 `C{序号}` 且呼号非空的卡片记录，避免线下换卡空呼号占位卡、`NC####` 不创建卡片占位记录和其他后台记录影响业务统计口径；其中待发卡片排除线上换卡签收链路记录、已签收、已收卡、`cardVersion=不发卡` 以及已经被 `ReceiveRecord.spec.outboundCardNames` 闭环关联的记录，仅保留仍需发卡处理的非线上换卡积压；已发卡片统计明确已发卡、已签收、有发卡时间的记录，`cardVersion=不发卡` 不纳入已发和签收统计，线上换卡中已制卡、已打包且制卡通知已发送的历史记录也纳入已发；已收卡片按 `ReceiveRecord.spec.callSign` 去重，呼号为空时按关联发卡 ID 去重。统计报表额外展示月度收发卡片折线图。
13. 审计中的卡片记录查询与收卡记录查询按业务场景 tab 展示，至少区分通联业务、线上换卡业务、线下换卡业务；卡片记录查询读取 `CardRecord`，收卡记录查询读取 `ReceiveRecord`。审计菜单保持只读查询和统计展示，不提供人工关联、创建、迁移等业务写操作。

## 9. 权限与安全
1. 权限遵循 `view/edit` 最小权限模型。
2. 服务端鉴权为准，前端仅做展示与导航控制。
3. 公开接口启用独立限流服务（按 IP/场景键）。
4. 审计日志覆盖关键写操作链路。
5. 本地卡片打印工具提供独立权限模板 `qsl-management-card-print-tool`（显示名“卡片打印工具”），通过依赖汇总 `qsl-management-station-profile-view`、`qsl-management-card-record-edit`、`qsl-management-qso-record-view`、`qsl-management-address-bureau-view`、`qsl-management-offline-activity-view`，便于为 Halo 个人令牌一次性授权打印、查询与回写所需权限；其中 `qsl-management-offline-activity-view` 为隐藏只读模板，仅授予 `offline-activities` 的 `get/list` 权限，用于线下换卡制卡队列活动筛选和 QTH 活动地点填充。
6. 控制台前端在 12 个带写操作的模块内直接创建 `qsl-audit-logs`，对应编辑模板统一依赖隐藏模板 `qsl-management-audit-log-write`（仅授予 `qsl-audit-logs/create`，2026-10-31 新增）。缺这条依赖时业务写入先成功、审计写入再返回 403。
7. 每个菜单权限节点必须有同名 Role 模板。`QslRoleTemplateContractTest` 已加两条反向校验：菜单引用的 `plugin:qsl-management:<节点>:view/edit` 必须存在模板；`QslConsoleApiEndpoint` 的每条路由按「路径首段资源 + 动词」必须能在 `console.api.qsl-management.bi1kbu.com` 规则里命中。

## 11. 本地打印工具（tools/CardPrint）
1. 主入口：
   - `python -m cardprint.cli ui online`
2. 当前作业流：
   - 配置登录 -> 卡片打印 -> 制卡确认 -> 打印封面（打包）-> 打包确认
   - 补打信封作为独立页签位于打包确认后，可按地址簿或卡片局主数据补打信封。
   - 自定义打印位于在线打印窗口最后一个页签，允许选择本地预设并手工填写模板要求的字段后执行单条打印。
3. 与后台关系：
   - 读取 QSL 后台卡片与地址信息生成打印队列。
   - 打印状态通过人工确认页签回写，避免自动误回写。
4. 在线桥接代码事实：
   - 默认 `base_url` 为 `http://localhost:8090`，但配置可传入其他地址。
   - 卡片/信封基础数据读取 `card-records`，卡片打印会按 `CardRecord.spec.qsoRecordName` 额外读取 `qso-records` 并注入 `qsoInfo`；通联业务制卡的发射地址字段优先使用 `QsoRecord.spec.myQth`，旧预设字段 `qth` 与新预设字段 `my_qth` 均按此规则取值，缺失时才兜底到对方 `qth`；线下换卡制卡仍优先使用关联活动的 `OfflineActivity.spec.activityLocation`；打印字段映射中 `CardRecord.spec.cardReceived` 为空或缺失时按未收卡处理，默认勾选“请回卡片”。
   - 信封打印纳入未打包（`envelopePrinted=false`）且卡片版本不是“不发卡”的卡片记录；信封补全会读取 `station-profiles`、`address-book-entries`、`bureau-entries`；封面打印页提供去向类型下拉筛选，去向国为空按国内卡片处理，存在去向国内容按国际卡片处理。打包确认使用同一未打包且非“不发卡”口径回写 `envelopePrinted`。
   - 补打信封读取 `address-book-entries` 与 `bureau-entries` 生成独立队列，复用信封预设，支持按呼号、地址编号或卡片局编号筛选，支持当前行打印、勾选批量打印与全部打印，不回写 `CardRecord` 状态。
   - 地址管理的待绑定地址呼号清单只统计仍需发卡的未绑定卡片；若呼号对应的未绑定正式卡片全部为 `cardVersion=不发卡`，不显示在待绑定清单中，地址自动绑定也跳过此类卡片。卡片异动中把卡片版本从“不发卡”改回实际卡片版本时，若尚未绑定地址且存在同呼号地址簿记录，自动回填第一条同呼号地址。
   - 补打眼球卡片使用独立页签和专用预设，预设路径保存到 `bridge_config.json` 的 `presets.eyeball_reprint_card`；页面手工输入呼号与日期时间，支持实时取当前日期时间，打印行固定 `cardType=EYEBALL`、“发出卡片”状态与“请回卡片”状态，不读取或回写 `CardRecord` 状态。
   - 自定义打印页根据本地预设 `fields` 与 `ui_schema` 动态生成文本、下拉和复选输入控件，跳过 `fixed_text` 固定文本字段；打印任务固定只包含当前一条数据，不访问 Halo 接口且不回写业务状态。页面不提供打印机和纸张选择，严格使用预设 `preferred_printer` 与 `paper.name`，最后一次预设路径持久化到 `bridge_config.json` 的 `presets.custom_single_print`。
   - 卡片版本列表通过公开接口 `GET /apis/api.qsl-management.bi1kbu.com/v1alpha1/exchange-online/-/station-cards` 读取，本质数据来源仍为 `station-cards`，不从 `card-records` 反推，并按 `sortOrder` 与版本号排序；本台通信地址仍通过受保护的 `station-profiles` Extension API 读取。
   - 线上换卡申请审核通过后点击“创建卡片”时，按申请地址复用或创建地址资源，并写入卡片记录的 `addressEntryName`。
   - 卡片二维码拼接支持 `qrcode.path_mappings` 短路径映射，在线打印配置页可在站点地址下方配置线下换卡、线上换卡、签收确认三类短路径；新配置默认分别映射为 `/eyeball`、`/online_eyeball`、`/rp` 后再追加卡片 ID 与 `cs` 参数，其中收卡回执采用极简 `/rp` 以缩短二维码内容，已有自定义映射保持不变。
   - 登录并拉取卡片版本时，网络请求在后台线程执行，避免界面短暂未响应；只补齐空白本台通信地址字段，不覆盖已有本台姓名、电话、邮编、地址。若受保护接口返回登录页或 HTML，工具明确提示认证或权限问题，不再静默解析为空数据。
   - 回写采用 Halo Extension 完整 `PUT`，先读取当前对象再合并 `spec`；`cardIssuedAt` 使用 `yyyy-MM-dd HH:mm:ss` 文本格式；回写会同步刷新 `CardRecord.status.flowStatus`，并按后台状态流转规则补齐或清理相关状态字段。
   - 打印预设字段支持 `fixed_text` 固定文本，用于固定辅助说明、提示语或版面标识；固定文本字段由标定工具维护，打印工具和在线打印工具不要求录入该字段，预览与打印时优先输出固定文本。
   - 打印预设的 `text_align（文本对齐）` 支持 `left（左对齐）`、`center（居中对齐）`、`right（右对齐）`，居中对齐以 `print_width_mm（打印宽度）` 为基准；`distribute_align（分散对齐）` 开启时优先于普通文本对齐。
   - 打印文本字段内容支持字面量 `/n` 和真实换行符强制换行，只识别小写 `/n`；即使打印宽度为 `0` 也保留强制分行，连续标记保留空行，`max_len（最大长度）` 不计算换行标记；二维码字段保持原始内容。
   - 打印预设字段新增 `print_border（是否打印边框）`，默认 `false`；开启时要求 `print_width_mm（打印宽度）`、`print_height_mm（打印高度）` 均大于 `0`，预览和实际打印按字段位置与宽高绘制一次细黑色边框，文本和二维码字段均适用。
   - 打印预设字段新增 `layout_mode（排版方式）`，支持 `horizontal（横向）`、`vertical（纵向）`、`mixed_vertical（混合纵向）`，默认横向。纵向将全部字形顺时针旋转 `90°`；混合纵向旋转 ASCII 英文字母、数字、英文冒号 `:` 和半角空格，中文、全角冒号 `：` 及其他字符保持正向并逐字排成一列；旋转后的半角内容按原字形宽度计算紧凑间距。
   - 纵向排版第一列位于字段区域最右侧，遇到 `/n`、真实换行或超过打印高度时从顶部向左换列，超过打印宽度后截断；左对齐、居中、右对齐分别表示顶部、垂直居中、底部对齐，分散对齐沿打印高度生效。
   - 纵向排版要求打印宽度和打印高度均大于 `0`，`digit_raise_ratio（数字上移比例）` 仅在横向生效；二维码字段忽略排版方式。
